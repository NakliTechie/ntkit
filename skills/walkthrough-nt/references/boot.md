## Phase 3 — Boot the app, the browser, and a session per role

Get a running app and a browser driving it:
- **If a harness already exists, run its `doctor` first** — it encodes this repo's specific freshness traps. The bullets below are the fallback for a repo that doesn't have one yet.
- **If the product file is generated or integrity-pinned, find the regenerator before your first edit.** Hand-editing a single-file app that pins its own CSP script hashes invalidates them and **bricks the app** — a blank page and a driver timeout, with nothing pointing at the cause. The instruction to "re-verify in the browser" quietly assumes edit-then-reload works; for a generated, hashed, or inlined product it does not. Find the sync target (`make`, a build script, a product-check `--write`) first, and record it in the feature map for the next run.
- **Start the app — prefer a production build over dev mode.** **For a zero-build product there is no build**: a single static file *is* the artifact, so serve it as shipped and say so, rather than inventing a build step to satisfy this line. Dev mode recompiles each route on first hit (slow, times out the driver) and isn't the bundle users actually run; a `build` + `start` is pre-compiled and fast. Dev is a fallback.
- **Derive every port from the checkout path, here in Phase 3 — not only in the Phase 6 harness.** Parallel runs are the normal case (a second walkthrough, an `/autopilot-nt` branch, a concurrent review of a sibling app), and a naive `base + n` scheme collides with them. Hash the worktree path to a port when the port must be **predictable** — something outside the process has to reach it. When the port only has to be **free** (a test server the suite itself connects to), bind port `0` and read back what the OS assigned; a random pick from a range is a lottery you eventually lose. One repo's harness drew from 8600-9399, which contains **9222 — Chrome's own remote-debugging port** — and had no `error` handler on `listen`, so a collision crashed the whole suite process with an unhandled `EADDRINUSE` instead of failing one test. Always attach that handler: a port collision must fail a check, never take the run with it. A collision surfaces as `EADDRINUSE` if you are lucky and as a walk driving *another app* if you are not.
- **Drive it with the browser tooling available** (the `preview_*` tools if present; otherwise Playwright or a browser MCP). Use explicit `127.0.0.1` and a known-free port — "localhost" can resolve to a different listener than the one you started.
- **WebGPU can't be tested headless.** Headless Chromium has **no WebGPU** — any flow that loads or runs a model in-browser via WebGPU (and other GPU-gated features) errors out headless. Drive those flows with the **Chrome MCP** (a real, GPU-backed Chrome), not headless Playwright; otherwise mark them untested.
- **Wait for the app to actually be ready before asserting** — a React/Next page returns blank if you read before hydration. Wait for `load` + `document.fonts.ready` + a short settle, not just `domcontentloaded`.
- **Enter as each role.** Prefer logging in *through the UI* (it exercises the real auth flow as that role); injecting a seeded session cookie is the fallback. Seed enough data that no page is a pure empty-state — **except** the first-run journeys, where empty *is* the thing under test. Draw from the **shared demo seed** (`demo/seed/` — the canonical asset `/demo-nt`, `/guide-nt`, and `/walkthrough-nt` all load); extend it when a feature lands, rather than inventing per-command seed data. **If `demo/seed/` does not exist**, use the repo's own fixture convention (`test/**/fixtures/`, a `?fixture=` query param, a seed script) and say in the report which you used; create `demo/seed/` only if the repo has no convention at all. Do not stall on a missing canonical asset.
- **Arm the invariant set before you start clicking.** Not "watch the console" — a **named list of conditions checked after every action**, each of which produces a finding with an ID when it breaks, exactly like a step that visibly failed. The floor set, borrowed from Bombadil's zero-spec browser defaults:

  | ID | Invariant |
  |---|---|
  | `INV-EXC` | no uncaught exception / `pageerror` |
  | `INV-REJ` | no unhandled promise rejection |
  | `INV-ERR` | no `console.error` |
  | `INV-HTTP` | no 4xx/5xx response, except ones the journey deliberately provokes |
  | `INV-SILENT` | every user-initiated action changed *something* observable — a toast, a dialog, a row, a status line, a route |
  | `INV-DIALOG` | no native `alert` / `confirm` / `prompt` |
  | `INV-DURABLE` | after anything that should persist, a reload returns the same state |

  **`INV-DURABLE` is in the floor set, not left to Phase 5 to invent.** Reload-after-mutation is the worst class of defect there is, and a practitioner who has to think of it themselves usually does so late or not at all. Write the oracle carefully: it must compare *everything* that should survive, not the convenient subset. An oracle that reads only the active tab, sheet, or pane will fire on a UI-state reset and report fabricated data loss — that failure mode has already produced a false Critical.

  **`INV-DIALOG` prevents a hang as well as catching a defect.** An unhandled `confirm()` blocks the driver and kills the run — no findings, no video. Register an auto-dismissing handler (`page.on("dialog", d => { log(d.type(), d.message()); d.dismiss(); })`) before the first click, so a native dialog becomes a finding instead of a dead session.

  **`INV-SILENT` targets the right failure and is the hardest of the set to implement well — treat it as a lead generator, not an oracle.** The dead button this command exists to find is quiet by definition: the handler threw or bailed, nothing was logged, the UI did not respond. But measured across two dogfood runs it fired 28 times and produced **zero** findings — 21 of 23 breaches on one app, 7 of 7 on another. Everything real came from `INV-DURABLE` and from unhandled throws. Budget for that signal-to-noise before you arm it.

  After any action, diff the DOM (or a cheap proxy — a text digest of the main region plus live-region content) against the state before it and flag a null delta. **Whitelist by *class*, not by step** — a random walk cannot enumerate its steps in advance, so per-step whitelisting does not survive Phase 5. The classes that are legitimately silent: caret moves at a boundary, downloads (invisible to a DOM diff unless the context sets `acceptDownloads`), native-seam cancels, and any control that renders into a detached card or overlay rather than the observed region.

  **`INV-SILENT` needs a repo-specific oracle on any canvas or WebGL surface, and is worse than useless without one.** The DOM-diff formulation assumes the UI *is* the DOM. Against a canvas-rendered grid or map, a working Bold, Align or checkbox changes pixels and internal state while the DOM digest sees nothing, so every real action reads as a silent failure — one run produced seven breaches, all false. On those surfaces, diff the app's own state (its model, a documented accessor, its agent face) instead of the DOM, or disable the invariant and say so in the report. A check with a 100% false-positive rate trains the reader to ignore the whole set.

  **Zero breaches across a whole run is normal and gets reported as zero.** This set catches noisy failure; a mature app's expensive failures are quiet. Do not read a silent invariant log as evidence the app is sound, and do not hunt for something to fill the slot. It also only sees what the driver does — a headless browser never requests a favicon, so an app's only 4xx can be invisible to `INV-HTTP`, while a **headed** one requests it and reports the 404 through the *console* channel rather than the `response` event. The channel-attribution warning given for `INV-REJ` applies here too: tag by cause, not by the pipe it arrived down, or your counts are fiction.

  **Implementing `INV-REJ`:** `pageerror` does not catch unhandled promise rejections, so surface them with an init script — `page.addInitScript(() => addEventListener("unhandledrejection", e => console.error("INV-REJ", e.reason)))` — and tag them, because they arrive through the console channel and will otherwise be counted as `INV-ERR`.

  Extend it with anything this repo protects — a budget (no bundle over N), a domain rule that must hold on every screen, or a sovereignty invariant. **Derive a repo-specific invariant from the repo's own declared policy, never from a plausible-sounding generality.** "No outbound request to a third-party origin" is the obvious sovereignty check and it is wrong: one run's fired 64 times on the first leg, on a CDN the repo's CSP pins and its locked decisions mandate, and on `127.0.0.1:11434`, which *is* the sovereign local-inference rung. Read the CSP, the handoff's locked decisions, and the doctrines; assert what the repo actually promised. Write the list into the report header so a reader knows what was being watched, and **attribute each breach to the action that preceded it** — an exception that fires three steps after the click that caused it is the normal case, not the exception.

  The point of naming them is that they catch what the scripted journey isn't looking at. A step can *look* correct — the right screen rendered, the right row appeared — while a handler threw on the way. Judgement checks the step; the invariants check everything the step didn't think to check.

  **If the app has no global error net, that absence is itself a finding** — an exception in an event handler otherwise produces *nothing* (no toast, no log), which is exactly how a dead button survives for months.

- **Record the run, and log every action.** Two artifacts, both into `plan/walkthrough-<date>-run/` (gitignored — a video is not a repo asset):
  - **A recording.** With Playwright this is one context option, so there is no excuse to skip it: `browser.newContext({ recordVideo: { dir: "plan/walkthrough-<date>-run/", size: { width: 1280, height: 720 } } })`. The file is only written on `context.close()`, so close the context in a `finally` — **and on `SIGINT`/`SIGTERM`**, because this walk spans many tool calls and a driver killed with `pkill` writes no video at all. Budget **1.2-1.7 MB per minute** at 720p. The file only lands on close, so segment deliberately rather than hoping to inspect mid-run. **Expect many files, not one:** Playwright writes one `page@<hash>.webm` per context, so a multi-leg walk ends with N unnamed files, some of them zero-byte. Plan for that from the start — write a `recordings.md` mapping each file to its leg and action-index range, and delete the empty ones. Without that artifact the recording is a pile of hashes nobody can navigate. If the driver genuinely cannot record, fall back to a screenshot per beat and say in the report that the recording is a contact sheet, not a video.
  - **An append-only action log** — one line per action: index, **timestamp relative to recording start** (`T0` — Playwright's video begins at zero, so wall-clock navigates nothing), role, journey step, the action **written as prose a reader can follow** ("clicked Save on the invite dialog", not `click(600,337)`), the selector or target, and any invariant that broke. This is what makes a finding *replayable* rather than described (Phase 5), and it is what the step narrative's timestamps point into, so a reader can jump to the moment in the recording instead of reading a repro paragraph.
